Ik ga een zeer lange wandelreis maken van Nederland naar Hanoi, Vietnam.

### Globale planning

* Vertrek: **eind juni 2027**
* Startpunt: Nederland, waarschijnlijk omgeving Lisse

# 17. TRACKING PRIVACY — BELANGRIJK

De standaardinstelling voor publiek moet zijn:

## Publiek = 14 dagen vertraging

Een normale bezoeker mag mijn huidige locatie **niet** zien.

Publieke bezoekers zien standaard alleen trackinggegevens die minimaal:

**14 dagen oud**

zijn.

Dus als ik vandaag ergens loop:

> publiek ziet die locatie pas ongeveer 14 dagen later.

Dit moet een configureerbare instelling in de backend zijn.

Bijvoorbeeld:

```text
public_tracking_delay_hours = 336
```

want:

14 × 24 = 336 uur.

De standaardwaarde is dus:

**336 uur / 14 dagen**

De waarde moet later eventueel kunnen worden aangepast naar bijvoorbeeld:

* 7 dagen
* 14 dagen
* 21 dagen
* 30 dagen

zonder dat de code aangepast hoeft te worden.

# 19. SERVER-SIDE TRACKING SECURITY

Dit is heel belangrijk.

De 14 dagen vertraging mag **niet alleen in de frontend worden toegepast**.

Dus NIET:

```text
API geeft alle GPS-punten
↓
JavaScript verbergt de laatste 14 dagen
```

Dat is onveilig.

De server moet de filtering uitvoeren.

Bijvoorbeeld conceptueel:

```text
PUBLIC API
    ↓
return only tracking points
where timestamp <= now - public_tracking_delay
```

En:

```text
PRIVATE API
    ↓
authenticated user
    ↓
trusted_viewer/admin
    ↓
return current tracking data
```

Een niet-geautoriseerde gebruiker mag de actuele GPS-coördinaten dus überhaupt niet via een API-response ontvangen.

Ook als iemand:

* DevTools gebruikt
* de API rechtstreeks aanroept
* een endpoint probeert te raden
* JavaScript inspecteert

mag hij geen actuele locatie kunnen ophalen.

Als je denkt dat een aparte frontend en API architectuur beter is, bijvoorbeeld:

```text
Laravel API
+
Next.js frontend
```

dan moet je **eerst uitleggen waarom**.

Je mag dit niet zonder overleg meteen bouwen.

Leg dan uit:

* waarom dit nodig is
* wat de voordelen zijn
* wat de nadelen zijn
* hoeveel extra complexiteit het oplevert
* waarom een Laravel monolith niet voldoende zou zijn

En vraag mij vervolgens om toestemming.

Pas daarna mag je die architectuur gebruiken.

# 42. DATA-ARCHITECTUUR

Belangrijk principe:

**Data moet één bron van waarheid hebben.**

Bijvoorbeeld:


# 45. GARMIN / TRACKING INTEGRATIE

De exacte Garmin-integratie moet nog worden onderzocht.

Ga niet zomaar aannemen dat Garmin een bepaalde API beschikbaar stelt.

Onderzoek eerst:

* welk Garmin-apparaat ik uiteindelijk gebruik
* welke dienst ik gebruik
* welke API beschikbaar is
* hoe trackingdata kan worden opgehaald
* hoe vaak data binnenkomt
* welke authenticatie nodig is
* wat de kosten zijn
* welke beperkingen gelden

Garmin-documentatie bevestigt dat trackingdata via inReach/MapShare kan worden gedeeld en dat tracking een actieve inReach-dienst vereist.

De website moet Garmin zien als een **bron van trackingdata**, niet als de volledige architectuur.

Mijn backend moet uiteindelijk de historische trackingdata zelf kunnen bewaren.
